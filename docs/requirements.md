## 1. 서비스 개요

책의 한 대목(발췌 문장)을 중심으로 독자들이 **익명으로** 감상을 교환하는 모바일 서비스.

### 1.1 핵심 개념

| 용어 | 정의 | 엔티티 |
|---|---|---|
| **대목** | 책에서 발췌한 문장. 여러 사람이 공유하는 단위 | `Passage` |
| **흔적** | 대목에 남긴 개인의 감상 | `Opinion` |
| **꾸밈** | 흔적/대목 텍스트에 적용한 밑줄·물결줄·형광펜 | `Decoration` |
| **댓글** | 흔적에 달리는 반응 (1 depth) | `Comment` |

### 1.2 설계 철학

두 가지 축이 서비스 전체를 관통한다.

1. **스포일러로부터의 보호** — 내가 읽은 만큼만 보인다
2. **저작권 준수** — 발췌는 150자, 페이지 이미지는 남기지 않는다

## 2. 인증 / 로그인

### FR-AUTH-01 로그인 트리거 (지연 로그인 모델)

**서비스는 비로그인 상태로 진입 가능하다.** 로그인 화면은 다음 4개 시점에만 노출된다.

| # | 트리거 | 설명 |
|---|---|---|
| 1 | 흔적 보기에서 **2페이지 이상** 열람 시도 | 첫 페이지만 무료 열람 |
| 2 | 흔적을 남기려 할 때 | 작성 진입 시점 |
| 3 | 답변(댓글)을 남기려 할 때 | 댓글 작성 시점 |
| 4 | 마이페이지 접속 | 탭 진입 시점 |

**로그인 유도 UX**
- 팝업 형태
- 문구: `해당 페이지부터는 로그인해야 확인할 수 있어요!`
- CTA: `[로그인 하러가기]` → 로그인 페이지로 이동

> **구현 주의**: 비로그인 사용자도 홈·책 상세·첫 페이지 흔적을 볼 수 있어야 하므로, 해당 API는 인증 없이 호출 가능해야 한다. Spring Security 설정에서 `permitAll` 범위를 명확히 구분할 것.

### FR-AUTH-02 소셜 로그인 제공자
- 카카오, 구글, 네이버 중 **최소 1개** (기획 노트: "한개만 되도 됩니다")
- 와이어프레임에는 `카카오로 계속하기` 단일 버튼
- **ERD에 `SnsProvider.APPLE`이 존재** → iOS 앱 심사 시 소셜 로그인이 있으면 Apple 로그인 필수(가이드라인 4.8). 앱 출시 계획이 있다면 반드시 추가

### FR-AUTH-03 약관 동의
- SNS 로그인 후 이용약관 페이지 **1회 동의로 가입 완료**
- 필수 2종: `이용약관 동의`, `개인정보 수집 및 이용동의`
- `약관 전체동의` 체크박스 제공
- 동의 시각 → `User.termsAgreedAt`

### FR-AUTH-04 닉네임 자동 생성 ★

가입 시 **형용사 + 명사** 조합으로 랜덤 부여. 중복 시 **뒤에 1~100 숫자** 부착.

**형용사 (30개)**
```
고요한, 다정한, 따스한, 느긋한, 단단한, 반짝이는, 맑은, 포근한, 조용한, 용감한,
성실한, 섬세한, 담백한, 신나는, 차분한, 자유로운, 깊은, 작은, 푸른, 은은한,
따뜻한, 빛나는, 소박한, 여유로운, 성숙한, 솔직한, 정다운, 특별한, 평온한, 부지런한
```

**명사 (30개)**
```
책갈피, 문장, 연필, 서재, 별빛, 달빛, 숲길, 잉크, 종이, 다락방,
찻잔, 산책자, 독서등, 노트, 고래, 나무, 파도, 구름, 여우, 다람쥐,
등불, 우체통, 시계, 지도, 여정, 쉼표, 낙엽, 창가, 이야기, 여백
```

**조합 수 계산**
- 기본 조합: 30 × 30 = **900개**
- 숫자 접미사 포함: 900 × 100 = **90,000개**

> **리스크**: 900명까지는 접미사 없이 가능하지만, 유저가 늘면 충돌이 급격히 증가한다(생일 역설). 900명 시점에서 이미 대부분 접미사가 붙는다. 90,000명이 상한이므로 MVP에는 충분하나, 단어 목록 확장 여지를 남겨둘 것.
>
> **구현**: `User.nickname`에 유니크 제약이 있으므로, 생성 → 저장 시도 → `DataIntegrityViolationException` 발생 시 재시도하는 낙관적 방식이 안전하다. 사전 조회 방식은 동시성에 취약하다.

### FR-AUTH-05 온보딩 (4단계)
- 로그인 직후 즉시 노출
- **마지막 페이지 외에는 모두 `SKIP` 가능**
- 캐릭터로 시선을 잡고 설명 전달

| 단계 | 카피 |
|---|---|
| 1 | 안녕하세요. {닉네임} 님! 교환 독서를 즐기러 오셨군요! |
| 2 | 사진을 통해 문장을 편하게 발췌할 수 있어요. |
| 3 | 내가 읽은 만큼 의견을 볼 수 있어요. |
| 4 | 그렇다면 교환독서를 해보러 가볼까요? |

- 완료 → `User.hasCompletedOnboarding = true`
- **캐릭터 디자인 완료 대기 중** (Figma에 명시)

## 3. 홈

### FR-HOME-01 도서 캐러셀
- 헤더: `지금 기록되고 있는 {N}권의 흔적들`
- **표시 권수 제한 없음** (현 단계 기준)
- 흔적이 남은 책의 **표지**가 보여짐
- **좌우 스와이프**로 탐색, 인터랙션 포함

### FR-HOME-02 책 정보 영역 (2-a)
캐러셀 중앙 책에 대해 표시:
- 책이름 + 작가명
- 남겨진 기록 수 → **대목별 / 흔적별 각각 표기**
- 클릭 시 → **발췌된 페이지 중 제일 첫번째 페이지**의 기록으로 이동
- 하단 정보에는 해당 책의 **모든 대목과 모든 흔적** 표기

### FR-HOME-03 검색
- 우측 상단 `검색` 아이콘
- 책 이름으로 **현재 서비스에 기록된 책**이 있는지 확인
- **결과 없을 시**: 기록되지 않았음을 명시 + 흔적을 남기겠냐고 유도

> 이 검색은 **외부 도서 API가 아니라 서비스 내부 DB 검색**이다. 흔적 남기기 플로우의 책 검색(외부 API)과 구분할 것.

### FR-HOME-04 하단 네비게이션

| 탭 | 동작 |
|---|---|
| **홈** | 메인 페이지로 복귀. 서비스 첫 접속 시 보이는 화면 |
| **+흔적 남기기** | 작성 플로우 진입. **현재 캐러셀 정중앙 책에 대해 남길지 먼저 묻고**, 아닐 시 직접 검색 |
| **MY** | 마이페이지 (내 기록 / 닉네임 변경 / 회원탈퇴 / 배경 컬러 변경) |

> `+흔적 남기기`의 "현재 책 먼저 제안" 동작은 홈 캐러셀의 상태를 알아야 하므로, 프론트에서 선택된 `bookId`를 파라미터로 전달하는 구조가 필요하다.

## 4. 책 상세 / 흔적 보기

### FR-VIEW-01 헤더 (1-a)
- 책 제목 + 뒤로가기 버튼
- 뒤로가기 → **메인으로 이동**

### FR-VIEW-02 페이지 네비게이션 (1-b)
- 발췌된 페이지들이 **오름차순**으로 나열 (예: `7p 9p 12p 23p 34p 121p 167p`)
- 스와이프 또는 클릭으로 활성화

### FR-VIEW-03 대목 표시 영역

#### 꾸밈 병합 표시 ★★
> 해당 대목에 **사람들이 꾸민 것이 한꺼번에 표기**된다.

**[타인 표기 노출 규칙]**

노출 대상 선정 (우선순위 순):
1. **1순위**: 공감(좋아요) 수 많은 순으로 **최대 3개** 선택
2. **2순위**: 공감 수 동일할 경우 → **최근에 남긴 순**
3. **3순위**: 날짜도 동일할 경우 → **랜덤 (서버에서 임의 선택)**

**겹침 처리**: 같은 글자·영역이 겹칠 경우 위 우선순위 기준으로 **상위 1개만 노출**, 나머지는 제외

> **구현 난이도 높음.** 이건 단순 조회가 아니라 서버에서 구간 겹침(interval overlap) 연산을 수행해야 한다.
>
> 알고리즘 개요:
> 1. 해당 Passage의 모든 Decoration을 `(likeCount DESC, createdAt DESC)` 정렬
> 2. 상위부터 순회하며 `[startOffset, endOffset)` 구간이 이미 선택된 것과 겹치는지 검사
> 3. 겹치지 않으면 채택, 겹치면 스킵
> 4. 3개 채택되면 종료
>
> 3순위 "랜덤"은 정렬 안정성을 깨뜨린다. 매 요청마다 결과가 바뀌면 사용자 혼란과 캐시 무효화를 유발하므로, **`Decoration.id`를 tiebreaker로 쓰는 결정적(deterministic) 방식**을 권장한다. 기획 의도는 "특정인이 항상 유리하지 않게"이므로, `id % N` 같은 고정 셔플로도 목적을 달성할 수 있다.

#### 대목 전환 (2-b)
- 같은 페이지에 **여러 대목**이 남겨진 경우 좌우 화살표로 넘겨봄
- 표시: `< 대목 2/4 >`
- **루프 형태** (마지막에서 다음 누르면 처음으로)

#### 스포일러 처리
- 스포일러 표기된 대목은 해당 페이지에서 **블러 처리**
- **[버튼]을 눌러야** 대목 + 흔적을 확인 가능

### FR-VIEW-04 스크롤 인터랙션 ★

두 가지 상태를 가진다.

| 상태 | 디자인 |
|---|---|
| 기본 | 포스트잇 형태의 대목 카드 |
| 스크롤 시 | 흔적을 보기 편한 형태로 변형 |

**레이아웃 규격**
- 상단: **대목 영역 270px 고정 (sticky)**
- 하단: 남은 공간 안에서 의견 스크롤
- 상단 책명 + 페이지 메뉴는 **고정 유지**

**변형 이유** (기획 명시): *의견마다 달라지는 꾸밈 정도를 확인하기 위함*

## 5. 흔적(의견) 목록

### FR-OPINION-01 기본 노출
- 남겨진 **모든 의견** 확인 가능 (스포일러 처리된 의견 제외)
- 스크롤로 계속 확인
- **의견은 최대 3줄까지 노출**, 초과 시 `...` 표기 → 클릭 시 전체 확인

### FR-OPINION-02 표시 항목 (3-a)
순서: `[닉네임]` → `[의견]` → `[남겨진 날짜]`

#### 날짜 표기 규칙 ★
| 조건 | 표기 |
|---|---|
| 24시간 미만 | `12시간 전` (시간 단위) |
| 1~3일 | `1일 전`, `2일 전`, `3일 전` |
| 3일 초과 | `yyyy-mm-dd` |

> 상대시간 계산은 **서버 시각 기준**으로 통일할 것. 클라이언트 로컬 시각을 쓰면 기기 설정에 따라 달라진다. 응답에 ISO-8601 원본을 함께 내려주고 표시 문자열은 프론트에서 생성하는 방식을 권장한다.

### FR-OPINION-03 정렬
- `N개의 흔적` 옆에 정렬 기능
- **최신 순 (default)** / **좋아요 순**

> ERD의 `idx_opinions_passage_sort (passage_id, like_count, created_at)` 인덱스가 이 요구사항과 정합한다. 다만 최신순이 default이므로 `(passage_id, created_at DESC)` 인덱스도 필요하다.

### FR-OPINION-04 액션 (3-b)

#### 좋아요
- 누르면 표기 변경 (토글)
- **100개 초과 시 `99+`로 고정 표기**

#### 댓글
- 댓글 아이콘 클릭 → 댓글 입력 페이지 이동 (또는 동일 페이지 내 입력도 허용)
- 남겨진 댓글도 함께 확인
- **대댓글 형태로 남겨지며, 대댓글에는 댓글을 남길 수 없음** (1 depth 확정)
- 추후 `@닉네임` 멘션 기능으로 알림 확장 예정

#### 신고하기 (추후 기능)
- 이상한 의견 신고
- 사유 선택 모달: **스팸 / 혐오 / 욕설 / 저작권 / 기타**

> 기획상 "추후 기능"이나, 앱스토어 심사 가이드라인 1.2는 UGC 서비스에 신고 기능을 요구한다. 웹 우선이면 미뤄도 되지만 **앱 출시 전에는 반드시 필요**하다.

### FR-OPINION-05 꾸밈 확인
- 하단 흔적에서 **각 의견 클릭 시** 해당 의견 작성자가 기록한 **문장 꾸밈 표기를 확인 가능**
- 즉, 상단 대목의 꾸밈이 해당 사용자 버전으로 전환됨

### FR-OPINION-06 권한
> 흔적 외 댓글은 **흔적을 남기지 않아도** 확인이 가능하며, 댓글 및 좋아요를 누를 수 있습니다.

- 흔적 작성 없이도 댓글·좋아요 가능 (로그인은 필요)

### FR-OPINION-07 댓글 상세 규칙
(와이어프레임 주석)
- 최대 **500자**
- 빈 댓글 등록 비활성화
- 내 댓글 수정·삭제 가능
- 원 댓글 아래 답글을 한 묶음으로 표시, **5개부터 `답글 더보기`**
- 흔적 외 댓글/답글에는 **좋아요 미제공**

### FR-OPINION-08 비로그인 열람 제한
- 남겨진 기록이 얼마 없을 경우 **2p~5p 정도** 노출
- **첫번째 페이지의 기록만 열람 가능**
- 다른 페이지 확인 시도 → 로그인 유도
- 댓글 남기려 할 때 → 로그인 유도

## 6. 흔적 남기기 (작성 플로우)

### 전체 흐름

```
[+흔적 남기기] 탭
   ↓
현재 캐러셀 중앙 책으로 남길지 확인
   ├─ 예 → [2] 로 점프
   └─ 아니오 ↓
[1] 책 선택 ──┬─ 1-a 최근 추가한 책 / 많이 등록된 책 리스트
              ├─ 1-b 검색
              └─ 1-c 직접 등록
   ↓
[바텀시트] 입력 방식 선택
   ├─ 1-a 📷 사진으로 입력 (OCR)
   └─ 1-b ✏️ 직접 입력
   ↓
[2] 문장 확정 (최대 150자)
   ↓
[2.5] 유사 문장 감지 → 병합 확인
   ↓
[3] 1/3 페이지 + 스포일러 + 읽기 상태
   ↓
[4] 2/3 꾸밈 효과
   ↓
[5] 3/3 흔적 작성 (최대 500자)
   ↓
```

### FR-WRITE-05 OCR 발췌 ★★

#### 2-a 촬영
- 원하는 문장이 포함된 부분을 사진으로 촬영
- 커스텀 디자인은 추후 업데이트

#### 2-b~c 인용 범위 안내 및 제한
> 사용자가 발췌를 저장하기 전에 **문장 중심의 인용 범위와 최대 150자 제한을 안내**.
> **책 페이지 이미지 전체와 150자를 넘는 원문은 노출하지 않습니다.**
> **공백·특수문자 포함 150자를 초과할 수 없으며, 초과 시 저장 버튼이 비활성화**된다.

- 안내 문구: `발췌하고 싶은 텍스트를 드래그해주세요. 최대 150자까지 가능해요.`
- 카운터: `0 / 150`
- **글자 수 계산은 공백·특수문자 포함** → `String.length()` 그대로 사용
- 초과 시 저장 버튼 disabled

#### 2-d 텍스트 확정
- 드래그한 문장이 **하단 인풋에 자동 입력**
- **직접 틀린 문장을 수정 가능한 텍스트 필드 형태** (기획서 02번 대응)

#### 2-e 초기화
- 다시 발췌하고 싶으면 **초기화 아이콘** 클릭 → 2-b 페이지로 복귀
- **발췌된 문장이 모두 지워지며 처음부터 다시 시작**

#### 이미지 처리 정책 ★★★
> **촬영 이미지는 OCR 처리 완료 후 즉시 폐기(영구 저장 금지). 텍스트 결과만 저장.**
> **서버 프록시 방식 확정(Feat/#7, `ClovaOcrClient`)**: 이미지는 디스크에 쓰지 않고 메모리에서만 처리해 즉시 폐기하며, 로그·APM에 남기지 않는다. ("서버 전송 자체를 금지"가 아니라 "서버에 영구 저장하지 않음"이 정확한 제약이다.)

이건 아키텍처를 결정하는 제약이다.

**함의**
- S3 업로드 **불필요** — 이미지가 영구 저장소에 올라가지 않는다
- `Book.coverImageUrl` 외에 이미지 저장소가 필요 없음
- 서버가 프록시하되 **저장하지 않고 스트리밍/메모리 처리**해야 함

**구현**: 서버 프록시 (메모리 처리) 방식으로 확정. `MultipartFile`을 디스크에 쓰지 않도록 `spring.servlet.multipart.max-in-memory-size`를 충분히 크게 설정하고, 요청 로깅 필터에서 해당 엔드포인트를 제외한다. 실수로 액세스 로그에 바이너리가 남으면 정책 위반이다.

### FR-WRITE-07 유사 문장 병합 ★★

- 카피(디자인): `기존 문장과 유사해요. 의견을 하나로 모을까요?`
- 카피(와이어프레임): `발췌하신 문장이 다른 분이 남겨준 문장과 비슷해 보이는데 의견을 합쳐도 괜찮을까요?`

**감지 조건**
> 사용자가 인용문을 저장하기 전, **같은 책의 동일하거나 인접한 페이지(±1)**에 유사한 발췌가 있으면 병합 확인 팝업을 표시한다.

**팝업 내용**
- `내가 발췌한 문장` vs `비슷한 문장` 양쪽 비교 노출
- 최대 150자 이내의 기존 발췌
- **연결된 의견 수** 표시
- 선택지: **함께 보기** / **내 발췌로 저장**

> **Passage 공유 모델(A안) 확정.** 여러 사용자의 Opinion이 하나의 Passage에 모인다.
>
> **`±1 페이지` 조건은 인덱스 설계에 직접 영향.** ERD의 `idx_passages_book_page (book_id, page_number)`가 이 조회에 정확히 맞는다. ✓
>
> **미결정**: "유사"의 판정 기준이 여전히 정의되지 않았다. 아래 중 택일 필요.
> - 정규화 후 완전 일치 (공백·구두점 제거 → 해시 비교) — 가장 단순, MVP 권장
> - 편집 거리(Levenshtein) 임계값 — OCR 오차 흡수 가능
> - 임베딩 유사도 — 과하다, MVP 부적합

### 9.3 Decoration 소유 주체 재확인 ★

기획 노트에서 새로 드러난 사실:

> 하단 흔적에서 **각각의 의견 클릭 시 해당 의견을 남긴 사람이 기록한 문장 꾸밈 표기**를 확인 가능

즉 **꾸밈은 Opinion에 종속**된다. 각 사용자가 같은 대목에 대해 서로 다른 꾸밈을 가진다.

현재 ERD의 `Decoration.opinion_id` 참조가 맞다. ✓

단, 노출 규칙(공감순 3개, 겹침 제거)이 **Decoration 단위**로 동작하므로, 조회 시 `Decoration → Opinion → likeCount` 조인이 필요하다. `Decoration`에 `likeCount`를 비정규화할지 검토 필요.

## 11. 개발 우선순위

### Phase 1 — 기반 (2주)
1. 소셜 로그인 (1종) + 약관 동의 + 닉네임 자동 생성

3. 도서 검색 API 연동 + 직접 등록
4. 홈 캐러셀 + 내부 검색

### Phase 2 — 작성 플로우 (3주)
5. 입력 방식 바텀시트
6. OCR 발췌 (150자 검증, 수정, 초기화)
7. 유사 문장 감지 및 병합
8. 페이지/스포일러/읽기 상태 설정
9. 꾸밈 효과 3종
10. 흔적 작성

### Phase 3 — 조회 및 소셜 (3주)
11. 책 상세 + 페이지 네비게이션
12. 대목 표시 + **꾸밈 병합 노출 규칙**

14. 흔적 목록 (정렬, 3줄 제한, 날짜 포맷)
15. 좋아요 (99+ 처리)
16. 댓글/답글 (1depth, 5개 접기)
17. 스포일러 블러 + 읽기 상태 필터

### Phase 4 — 마이페이지 (1.5주)
18. 프로필 + 최근 흔적
19. 닉네임 변경 (1일 1회)

22. 배경 변경, 스포일러 관리, 공지사항
